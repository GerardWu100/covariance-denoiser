Covariance Denoiser: reading the code

What each module does, how the pieces connect, where the timing rules live, and what the run found.

How to use this

Sections follow the order in which the code runs. Every snippet comes from src/covariance_denoiser/. Numbers in grey Sample data boxes come from the pipeline run on the tracked price file on 2026-08-10. Coloured boxes mark design choices, traps, and weaknesses.

The process in plain English

The project asks whether cleaning a covariance matrix helps forecast the next month's volatility for a basket of exchange-traded funds. It loads seventeen years of daily closing prices for eight funds, turns them into returns, and estimates three covariance matrices from the previous sixty-three days: the plain estimate, a shrunk estimate, and one with noisy directions filtered out. Seven values from those matrices are used to predict the next twenty-one days of realized variance. The answer is no: the simple rule that predicts next month's variance from the previous month's variance beats the fitted model on both error measures.

01The question and the answer

The research question, taken word for word from README.md: "Do denoised covariance features improve next-window realized variance forecasts for a small ETF universe in an offline reproducible workflow?"

Three terms will appear throughout this page:

  • Covariance matrix. A square table whose cell $(i,j)$ measures how fund $i$ and fund $j$ move together. The diagonal holds each fund's variance. With eight funds, it is an 8×8 table.
  • Denoising. A covariance matrix estimated from only sixty-three days of data contains substantial noise. Denoising replaces it with a more stable estimate. This project tries Ledoit-Wolf shrinkage and random matrix theory filtering. Both are defined in section 06.
  • Realized variance. The sum of a portfolio's squared daily returns over a window. It measures the volatility that actually occurred.

Why the negative result matters

The important part is the timing machinery in section 08. It makes the negative result credible. Volatility-forecasting code often appears to beat a benchmark because future information leaks into a label. This code blocks that leak and reports that it did not beat the benchmark.

Three ways to start it

1. Installed command. uv run covariance-denoiser run-offline-demo — declared in pyproject.toml under [project.scripts], pointing at covariance_denoiser.cli:main.
2. Shell wrapper. ./scripts/run_offline_demo.sh — changes to the repository root, then runs the same command.
3. Notebook. notebooks/01_offline_research_pipeline.ipynb — calls the same package functions stage by stage and shows the intermediate frames.

The second command, refresh-raw-cache, is the only repository code that touches a database. Normal runs, tests, and the notebook never call it.

Why the layout is split into modules

Each module has one job. A reviewer can check target construction without reading the model code, and tests can check one contract at a time. The trade-off is that tracing one number end to end takes seven files. In return, the tests in tests/unit/targets/ and tests/unit/models/ can lock down the timing rules without running the whole pipeline.

There is no config.toml. Each setting is a command-line flag with its default in cli.py.

One tunable number is not a flag. In features/covariance_features.py, DEFAULT_TRAILING_VOL_DAYS = 21 sets the length of the trailing volatility feature and cannot be changed from the command line. 04Reading the data — raw_cache.py, prices.py

validate_raw_cache — reject the wrong file

In plain words

Before doing any arithmetic, it checks that the price file on disk is the expected file. If not, it stops with a clear message.

What it does

Input: a directory path. Output: a small frozen record with a yes/no flag, a message, and the two file paths. Role: load_raw_prices calls it and raises FileNotFoundError if the flag is false. No later module sees an unchecked file.

It checks that both files exist, that the JavaScript Object Notation (JSON) metadata parses to an object, that all eight required keys are present, and that the parquet columns are exactly ['date', 'asset', 'close']. It then checks the row count, fund symbols, first and last dates, frequency "1d", price field "close", and is_adjusted_close True.

Why check is_adjusted_close at all

Adjusted closing prices include dividends and share splits. Unadjusted prices show a large artificial drop on each split and dividend date. Because the project measures squared returns, one unadjusted split could create a false volatility spike large enough to change the results. The metadata flag makes adjusted prices a requirement.

build_log_return_matrix — reshape prices into returns

wide_prices = prices.pivot(index="date", columns="asset", values="close").sort_index()

log_prices = np.log(wide_prices)
log_returns = log_prices.diff().dropna(how="any")
log_returns.index = pd.to_datetime(log_returns.index)
return log_returns
The formula

$$r_{i,t}=\log\left(\frac{P_{i,t}}{P_{i,t-1}}\right)=\log P_{i,t}-\log P_{i,t-1}$$

$P_{i,t}$ is fund $i$'s adjusted closing price on day $t$. $r_{i,t}$ is its log return, written as a decimal; 0.0090 means about +0.90 per cent. Log returns add across days, which lets the target in section 05 use a simple sum.

Trap

dropna(how="any") drops a whole date when any fund is missing. It does not fill or interpolate. The tracked file loses nothing, but a later-listed fund or a half-day with no price for one fund would also remove the other seven funds' returns for that date. The following day's return would then span two calendar days, with no log message.

05The forecast target — realized_variance.py

compute_equal_weight_portfolio_log_returns — eight funds into one basket

asset_simple_returns = np.expm1(returns)
portfolio_simple_returns = asset_simple_returns.mean(axis=1)
return np.log1p(portfolio_simple_returns).rename("equal_weight_portfolio_log_return")
In plain words

It turns eight daily fund returns into one number: the return of a basket with equal dollar amounts in each fund, rebalanced every day.

The formula

$$r_{p,t}=\log\left(1+\frac{1}{N}\sum_{i=1}^{N}\left(e^{r_{i,t}}-1\right)\right)$$

$r_{i,t}$ is fund $i$'s log return on day $t$; $e^{r_{i,t}}-1$ converts it to a simple return; $N=8$ is the number of funds; and $r_{p,t}$ is the portfolio's log return. The calculation converts each log return, averages the simple returns, then takes the log again.

Why it averages simple returns first

Averaging log returns describes a basket whose weights drift because it is never rebalanced. Averaging simple returns first describes a basket rebalanced to equal weights each day. The one-day gap is small, but the project sums squared portfolio returns, so a consistent return bias also biases the target. The repository journal records this as an audit fix. A unit test, test_equal_weight_portfolio_return_averages_simple_returns_first, keeps the correction in place.

compute_forward_realized_variance_target — create the label

equal_weight_returns = compute_equal_weight_portfolio_log_returns(returns=returns)
squared_equal_weight_returns = equal_weight_returns.pow(2)

# Rolling sum over the next `horizon_days` squared returns; shift aligns label to today.
forward_realized_variance = (
    squared_equal_weight_returns.rolling(window=horizon_days).sum().shift(-horizon_days)
)
What it does

Input: the wide return matrix, a horizon $h$, and whether to annualize. Output: one value per date for the realized variance of the next $h$ days. Role: this is what the models predict. The last $h$ rows are empty because their future has not happened yet.

The formula

$$\mathrm{RV}_{t,h}=\sum_{j=1}^{h}r_{p,t+j}^{2} \qquad\text{and}\qquad \mathrm{RV}^{\text{ann}}_{t,h}=\mathrm{RV}_{t,h}\cdot\frac{A}{h}$$

$r_{p,t+j}$ is the portfolio log return $j$ days after day $t$; $h$ is the horizon in trading days, 21 by default; $A$ is trading days per year, 252 by default. The sum starts at $j=1$, not $j=0$: day $t$'s own return is excluded. The factor $A/h$ annualizes a 21-day sum, so 0.03 means an annualized volatility of $\sqrt{0.03}\approx 17.3$ per cent.

Trap: the sign of the shift

.rolling(21).sum() looks backwards: at row $p$ it holds rows $p-20$ through $p$; the same window is rows $p-20$ through $p$ before .shift(-21) moves its value 21 rows earlier, onto row $p-21$. Those are the 21 days strictly after $p-21$. A wrong shift sign, or shifting by 20 instead of 21, puts day $t$'s own return in its label. The test test_forward_realized_variance_uses_future_returns_only checks this with four hand-computed rows.

06Three covariance estimates

All three use the same return window: the last 63 days × 8 funds by default. Each returns an 8×8 covariance matrix with fund names attached. Only the method differs.

estimate_sample_covariance — the basic estimate

def estimate_sample_covariance(returns_window: pd.DataFrame) -> pd.DataFrame:
    """Estimate sample covariance from aligned return observations."""
    return returns_window.cov()
The formula

$$\hat{\Sigma}_{ij}=\frac{1}{T-1}\sum_{s=1}^{T}\left(r_{i,s}-\bar{r}_i\right)\left(r_{j,s}-\bar{r}_j\right)$$

$T$ is the number of days in the window (63); $r_{i,s}$ is fund $i$'s return on day $s$; and $\bar{r}_i$ is its window average. Dividing by $T-1$ rather than $T$ corrects for estimating that average from the same data.

covariance_to_correlation — remove the volatility scale

The formula

$$C_{ij}=\frac{\Sigma_{ij}}{\sqrt{\Sigma_{ii}\,\Sigma_{jj}}}$$

$\Sigma_{ii}$ is fund $i$'s variance, so $\sqrt{\Sigma_{ii}}$ is its volatility. Dividing by both volatilities leaves a co-movement value between $-1$ and $+1$. The code clamps each variance at $10^{-12}$ before taking the square root, preventing division by zero for a fund that never moves. It then makes the matrix exactly symmetric and puts exact ones on the diagonal to remove floating-point drift.

estimate_ledoit_wolf_covariance — pull the estimate toward a simple shape

In plain words

It blends the noisy sample matrix with a simple, stable matrix and chooses the blend proportion automatically.

The formula

$$\Sigma_{\text{LW}}=(1-\delta)\,\hat{\Sigma}+\delta\,F,\qquad F=\mu I,\qquad \mu=\frac{\operatorname{tr}(\hat{\Sigma})}{N}$$

$\hat{\Sigma}$ is the sample covariance. $F$ is the target: average variance $\mu$ on the diagonal and zeros elsewhere. $I$ is the identity matrix; $\operatorname{tr}$ sums the diagonal; $N=8$ is the number of funds; and $\delta$ is the shrinkage intensity, between 0 and 1. The Ledoit-Wolf rule chooses $\delta$ to minimise expected squared error. The code calls sklearn.covariance.LedoitWolf and re-attaches the fund names.

estimate_rmt_covariance — filter noisy directions

eigenvalues, eigenvectors = np.linalg.eigh(sample_correlation.to_numpy())

# Marcenko-Pastur upper edge for the noise bulk (T observations, N assets).
observation_count = float(len(returns_window))
asset_count = float(returns_window.shape[1])
aspect_ratio = observation_count / asset_count
lambda_plus = (1.0 + aspect_ratio**-0.5) ** 2

# Replace noise eigenvalues with their average rather than zeroing them out.
noise_mask = eigenvalues <= lambda_plus
if noise_mask.any():
    eigenvalues[noise_mask] = float(eigenvalues[noise_mask].mean())
In plain words

Break the correlation matrix into independent directions. The theory gives a cutoff for how large a direction can appear by chance with only sixty-three days of data. Directions below the cutoff are treated as noise and set to their average. The matrix is then rebuilt.

The formula

Step 1, the noise ceiling from Marchenko-Pastur theory:

$$q=\frac{T}{N},\qquad \lambda_{+}=\left(1+q^{-1/2}\right)^{2}$$

Step 2, flatten every eigenvalue at or below that ceiling to their common average:

$$\tilde{\lambda}_k=\frac{1}{|\mathcal{N}|}\sum_{m\in\mathcal{N}}\lambda_m \quad\text{for every }k\in\mathcal{N},\qquad \mathcal{N}=\{\,m:\lambda_m\le\lambda_{+}\,\}$$

Step 3, rebuild, rescale the diagonal back to one, then reattach the volatilities:

$$\tilde{C}=V\,\operatorname{diag}(\tilde{\lambda})\,V^{\top},\qquad \Sigma_{\text{RMT}}=D\,\tilde{C}_{\text{norm}}\,D,\qquad D=\operatorname{diag}(s_1,\dots,s_N)$$

$T$ is the number of days in the window (63); $N$ is the number of funds (8); $q$ is their ratio; and $\lambda_+$ is the largest direction size expected from chance alone. $\lambda_m$ is the $m$-th eigenvalue of the sample correlation matrix, sorted ascending. $\mathcal{N}$ is the set judged to be noise and $|\mathcal{N}|$ is its size. $V$ holds the eigenvectors as columns. $\tilde{C}_{\text{norm}}$ is the rebuilt matrix rescaled to a diagonal of one. $s_i$ is fund $i$'s sample standard deviation over the window. Replacing noise with its average, rather than zero, keeps the eigenvalue total unchanged and preserves the funds' variances.

Across all 4216 tracked windows, only one eigenvalue survives the cutoff in 4060 of them (96.3 per cent); two survive in the remaining 156. In practice, the random matrix theory filter reduces the eight funds to one common factor on almost every day.

The limitation

Marchenko-Pastur theory describes what happens when the number of funds and days both grow large. Here $N=8$, which is not large. The cutoff $\lambda_+ = 1.8397$ is fixed because $q=63/8$ never changes, so the filter uses the same threshold in calm and crisis markets. GUIDE_OVERVIEW.md calls this "a filtering heuristic", which is accurate.

Trap: the condition number also reflects volatility spread

The cleaned correlation matrix has a condition number of 7.57 in the last window. The cleaned covariance matrix has 91.08, twelve times more. That difference is not noise; it comes from the spread of fund volatilities. Daily volatilities range from 0.00261 (HYG) to 0.01325 (IWM), a ratio of 5.08. Because covariance scales with squared volatility, $5.08^2 = 25.8$. Three of the seven features therefore partly measure volatility differences, not denoising quality.

07The seven predictors — covariance_features.py

for end_index in range(lookback_days - 1, len(returns)):
    window_start = end_index - lookback_days + 1
    in_sample_window = returns.iloc[window_start : end_index + 1]
    window_timestamp = pd.Timestamp(returns.index[end_index])

    # Three estimators share the same in-sample window; only post-processing differs.
    covariances = {
        "sample": estimate_sample_covariance(in_sample_window),
        "ledoit_wolf": estimate_ledoit_wolf_covariance(in_sample_window),
        "rmt": estimate_rmt_covariance(in_sample_window),
    }
In plain words

Move a 63-day window one day at a time across seventeen years. At each stop, build the three covariance matrices and reduce them to seven numbers. Stamp the row with the window's last day.

What it does

Input: the 4278×8 return matrix and a lookback length. Output: a 4216×7 table indexed by window-end date. Role: the model inputs. Runtime: about 8 seconds for the full history; it fits 4216 × 3 = 12,648 covariance matrices in a plain Python loop.

The formulas behind the seven columns

Condition number of a covariance matrix, used three times:

$$\kappa(\Sigma)=\frac{\lambda_{\max}(\Sigma)}{\lambda_{\min}(\Sigma)}$$

Average pairwise correlation, over the pairs above the diagonal only:

$$\bar{\rho}=\frac{2}{N(N-1)}\sum_{i\lt j}C_{ij}$$

Trailing annualized volatility of the basket:

$$\sigma_t=\sqrt{A}\cdot\operatorname{sd}\!\left(r_{p,t-20},\dots,r_{p,t}\right)$$

$\lambda_{\max}$ and $\lambda_{\min}$ are the largest and smallest eigenvalues, so $\kappa$ grows as the matrix becomes harder to invert. $C_{ij}$ is the correlation between funds $i$ and $j$; $N=8$, so there are $N(N-1)/2 = 28$ pairs. $\operatorname{sd}$ is the sample standard deviation, using the $T-1$ divisor over the last 21 portfolio returns; $A=252$.

Why the row uses the window's last day

A feature row stamped $t$ uses returns through day $t$, so it is known at that day's close. The target stamped $t$ covers days $t+1$ to $t+h$. Joining on the date matches what was known at the close of $t$ with what happened next. Moving the feature stamp forward loses information; moving it backward leaks it.

Trap: the ratio denominator is never small

The code guards the two ratio features with max(sample_condition_number, 1e-12). That guard can never fire: a condition number is the ratio of the largest to smallest eigenvalue of a positive matrix, so it is always at least 1. The real risk is the opposite: the denominator can reach 1396 in a stressed window, pushing the ratio toward zero precisely when the regime matters most.

08Timing and training — walk_forward.py, baselines.py

This is the core of the repository. The other sections support it.

The timing problem in one picture

A label stamped on day $t$ sums returns from $t+1$ to $t+h$. It is unknown until the close of day $t+h$. At forecast time $t_0$, the latest usable label is therefore stamped $t_0-h$; the $h-1$ labels after it are still forming.

generate_walk_forward_slices — create the gap

# A target at position t uses returns t+1 through t+h and is known at t+h.
# Starting at min_train_size + h - 1 preserves the requested count of fully
# observed training labels while purging the h - 1 unavailable labels.
test_start = config.min_train_size + config.target_horizon_days - 1
while test_start + config.test_size <= sample_count:
    train_stop = test_start - config.target_horizon_days + 1
    train_slice = slice(0, train_stop)
    test_slice = slice(test_start, test_start + config.test_size)
    slices.append((train_slice, test_slice))
    test_start += config.step_size
The formula

For a fold whose test block begins at row $s$:

$$s_0=m+h-1,\qquad s_{k+1}=s_k+\Delta,\qquad \text{train}=[0,\;s-h+1),\qquad \text{test}=[s,\;s+n)$$

$m$ is min_train_size (252); $h$ is target_horizon_days (21); $\Delta$ is step_size (21); $n$ is test_size (21); $k$ counts folds from zero. The gap is $s - (s-h+1) = h-1 = 20$ rows. The first test row starts at $m+h-1$, not $m$, so training still contains the requested $m$ rows.

Why chronological order is not enough

The usual rule is "train on the past, test on the future". Here that would mean training on rows 0 through 271 and testing from row 272. It is wrong: the label on row 271 sums rows 272 to 292, the days being forecast. Training on it gives the model the answer. scikit-learn's TimeSeriesSplit makes the same mistake with overlapping forward-looking labels. Purging $h-1$ rows fixes it, and test_walk_forward_slices_respect_train_before_test asserts the arithmetic.

The formula

$$\hat{y}_t=\mathrm{RV}^{\text{ann}}_{t-h,\,h}$$

$\hat{y}_t$ is the forecast made at the close of day $t$. $\mathrm{RV}^{\text{ann}}_{t-h,h}$ is the annualized realized variance over days $t-h+1$ to $t$, the month that just ended. It became fully known at the close of day $t$. In plain words: next month's variance will match the month that just ended.

What the error check prevents

If the shift ran off the front of the series, .loc[test_index] would return empty values and the error metrics could use fewer rows or NaN. The explicit raise stops that silent distortion. It is one of the few places where the code refuses to continue.

# Ridge is not scale invariant. Fit the scaler on each training fold so

The formula

Standardize each predictor with the training fold's average and spread:

$$z_{j}=\frac{x_{j}-\mu_{j}^{\text{train}}}{\sigma_{j}^{\text{train}}}$$

Then fit ridge regression, which is least squares with a penalty on the size of the coefficients:

$$\hat{\beta}=\arg\min_{\beta}\;\left\lVert y-Z\beta\right\rVert_{2}^{2}+\alpha\left\lVert\beta\right\rVert_{2}^{2} \;\;\Longrightarrow\;\; \hat{\beta}=\left(Z^{\top}Z+\alpha I\right)^{-1}Z^{\top}y$$

Finally clip the forecast into the range a variance can live in:

$$\hat{y}=\max\!\left(0,\;z^{\top}\hat{\beta}+\hat{\beta}_0\right)$$

$x_j$ is feature $j$ before scaling; $\mu_j^{\text{train}}$ and $\sigma_j^{\text{train}}$ are its average and standard deviation computed only from that fold's training rows; $z_j$ is the standardized value; $Z$ is the standardized training matrix; $y$ is the training-label vector; $\alpha$ is --ridge-alpha, fixed at 1.0; $\beta$ is the coefficient vector; $\hat\beta_0$ is the intercept; and $I$ is the identity matrix. Solving the objective's derivative for $\beta$ gives the displayed form, which scikit-learn computes.

Why the scaler stays inside each fold

There are two reasons:

Scale. The seven features have very different scales: condition numbers reach 1396 while trailing volatility is near 0.12. Ridge penalizes all coefficients equally. Without standardization, large condition-number inputs would dominate the penalty and make it meaningless.

Leakage. A scaler fitted over the whole history would use 2020 values when standardizing 2009 data. That leaks future information into the past. Keeping it inside make_pipeline means .fit() sees only the training rows for that fold.

The calibration problem

The zero floor fires on 784 of 3906 forecasts, 20.1 per cent. The most negative raw forecast is $-0.1555$, while the average realized value is $0.0158$. A model that predicts an impossible value one time in five is badly miscalibrated; the clip hides the extent of the problem. Because clipping happens before scoring, the reported ridge error is better than the raw model's error, and it still loses.

09Scoring and output files

The formula

$$\mathrm{MAE}=\frac{1}{n}\sum_{t=1}^{n}\left|y_t-\hat{y}_t\right| \qquad \mathrm{RMSE}=\sqrt{\frac{1}{n}\sum_{t=1}^{n}\left(y_t-\hat{y}_t\right)^{2}}$$

$y_t$ is the realized annualized variance; $\hat{y}_t$ is the forecast; and $n=3906$ is the number of scored days. Mean absolute error (MAE) weights each miss by its size. Root mean squared error (RMSE) squares each miss first, so a few large misses dominate. Both use the target's units and can be compared directly with the average target value of 0.0158.

Why the measures rank the models the same

For mean absolute error, the naive rule wins by a wide margin: 0.0106 versus 0.0184. For root mean squared error, the gap nearly closes: 0.0340 versus 0.0354. Both models miss rare, large variance spikes. Squaring those misses makes them dominate the second measure, so both models look similarly poor there. Ridge is clearly worse on typical days and about as weak on the worst days.

10The optional database refresh — clickhouse_refresh.py

In plain words

One command connects to a ClickHouse database, pulls prices, and rewrites the parquet file and its metadata. Nothing else calls it.

What it does

Input: connection settings, a date range, and fund symbols. Output: overwrites raw_prices.parquet and raw_prices.metadata.json. Role: a one-time refresh path. The metadata it writes is the same contract that validate_raw_cache checks, so both ends agree.

Two things to know before running it

It overwrites without asking. There is no backup, confirmation, or dry-run. If the query returns fewer rows than expected, the tracked reference dataset is replaced and the repository's results change.

The password is a command-line flag. It goes into your shell history and process list, where other users on the machine may read it. The repository has a .env file, but no code reads it.

ConstructWhat it doesThe trap
.rolling(h).sum().shift(-h)Sum the next $h$ values and stamp the result on todayThe rolling window looks backward and the shift is negative. Change either one and today's return leaks into today's label.
np.expm1 / np.log1pConvert log returns to simple returns and backThey preserve precision for small $x$, the size of a daily return. They implement exp(x)-1 and log(1+x); the round trip also requires averaging in between. Averaging log returns directly gives the wrong portfolio.

15If someone points at a line

The questionThe answer
"Where exactly is look-ahead bias prevented?"Three places. (1) The target's .shift(-h) starts the sum at $t+1$, so a label excludes its own day. (2) generate_walk_forward_slices stops training $h-1$ rows before testing, so no training label overlaps the test period. (3) StandardScaler is inside the fold pipeline, so its statistics use training rows only.
"Prove the purge width is right, do not just assert it."Fold 0 ends training on 2009-04-01 and starts testing on 2009-05-01. The naive forecast for 2009-05-01 is 0.086617, the same as the label stamped 2009-04-01. The last usable training label and the latest observable label are the same row. One wider row would use future information.
"Why not just use scikit-learn's TimeSeriesSplit?"It preserves order but puts testing immediately after training. With labels that look 21 days forward, the last 20 training labels partly use test-period returns. This code purges those 20 rows; TimeSeriesSplit does not.
"Are the reported errors statistically valid?"No, as the README says. Neighbouring 21-day targets share 20 of their 21 days, so the 3906 forecasts are not 3906 independent observations. MAE and RMSE are descriptive comparisons, not a significance test. A proper test would need an uncertainty estimate that accounts for overlap, such as Newey-West.
"Why is ridge_raw_prediction in the output when you also report the clipped one?"To make clipping auditable. It fires on 784 of 3906 forecasts (20.1 per cent); the worst raw value is $-0.1555$ versus an average realized value of $0.0158$. Without that column, the floor's effect would be hidden.
"What happens if I set --horizon-days 63?"The target window, purge width, and naive lag move to 63 automatically. DEFAULT_TRAILING_VOL_DAYS stays at 21. Nothing errors, but trailing volatility no longer matches the horizon.
"How long does a run take?"About 20 seconds on the tracked data. Roughly 8 seconds are spent in the feature loop, which fits 12,648 covariance matrices one at a time in Python. The 186 ridge fits take little time by comparison.
"Why does the random matrix theory filter help conditioning less than shrinkage?"It filters the correlation matrix, then restores the volatilities. Their spread alone adds a factor of about 26 to the last window's condition number. Ledoit-Wolf shrinks the full covariance matrix, including volatilities. The values 91.08 and 9.12 therefore measure different things.
"Is eight funds enough for random matrix theory?"No. The theory assumes both $N$ and $T$ are large, but $N=8$. On the real data, the filter keeps one eigenvalue in 96.3 per cent of windows, so it acts like a one-factor model rather than a detailed clean-up.
"Where does the run write its files if I do not pass --output-dir?"To outputs/demo under the repository root, resolved from the package's file location. Before section 11, it used the current shell directory instead.

17Limitations, stated honestly

One universe, horizon, and feature set

The study uses eight funds, one 63-day lookback, one 21-day horizon, one feature set, one fixed ridge penalty, and one price history. Because nothing was varied, the negative result may be specific to this setup rather than denoised covariance features in general. Nothing was tuned, so it is not the result of a search over settings.

The error measures cannot show significance

Neighbouring targets share 20 of their 21 days. The 3906 forecasts contain far less independent information than the count suggests. Comparing 0.010610 with 0.018354 shows that the naive rule is better here; it does not show that the gap is statistically significant, and the code does not claim that it is.

Condition numbers are a weak proxy for investment use

The project measures denoising quality by how easy the matrix is to invert. That is a numerical property, not a financial one. It does not test whether the cleaned matrix produces better portfolio weights, lower turnover, or better hedges — the practical uses of covariance cleaning. GUIDE_OVERVIEW.md says this separation is intentional, but it limits what the negative result means.

The model is a poor match for the target

It is a linear regression on seven features with a penalty of 1.0 that was never tuned. The target cannot be negative and is strongly right-skewed, yet the model violates the non-negativity constraint one time in five. Modelling the logarithm of variance would be a sensible alternative because it is roughly symmetric and cannot produce a negative forecast. The negative result partly reflects the model choice, not only the features.

No transaction costs, investability, or held-back data

There is no trading, so there are no costs. There is also no evidence that a better variance forecast would have been useful. The tracked file ends 2024-12-31, so the pipeline's entire history was available during development. There is no held-back period.
