Covariance Denoiser: reading the code

What each module does, how the pieces feed each other, where the timing rules live, and what the pipeline actually found when it was run.

How to use this

Sections follow the order the code runs. Every snippet is copied from the files under src/covariance_denoiser/. Every number in a grey Sample data box came from running the real pipeline on the tracked price file on 2026-08-10, not from an estimate. Coloured boxes flag design choices, traps, and honest weaknesses.

The process in plain English

The project asks one question: if you clean up a covariance matrix, do the numbers you get out of the cleaned matrix help you forecast how volatile a basket of exchange-traded funds will be over the next month? It loads seventeen years of daily closing prices for eight funds, turns them into returns, and for every day computes three versions of the covariance matrix from the previous sixty-three days: the plain one, a shrunk one, and one with its noisy directions filtered out. It squeezes those three matrices into seven numbers, and tries to predict the next twenty-one days of realized variance from them. The honest answer it lands on is no: a simple "last month looked like this, next month will look the same" rule beats the fitted model on both error measures.

01The question, and the answer the code found

The research question, taken word for word from README.md: "Do denoised covariance features improve next-window realized variance forecasts for a small ETF universe in an offline reproducible workflow?"

Two terms first, because the rest of the page leans on them.

  • Covariance matrix. A square table. Cell $(i,j)$ says how much fund $i$ and fund $j$ move together. The diagonal holds each fund's own variance. With eight funds it is an 8×8 table.
  • Denoising. A covariance matrix estimated from only sixty-three days of data is mostly noise. Denoising means replacing the estimate with something better behaved. This project tries two recipes: Ledoit-Wolf shrinkage and random matrix theory filtering. Both are defined in section 06.
  • Realized variance. Add up the squared daily returns of a portfolio over a window. It measures how bumpy the ride actually was, after the fact.

Why a negative result is still worth reading

The value of this repository is not the model. It is the timing machinery in section 08 that makes the negative result believable. Most volatility-forecasting code that "beats the benchmark" does so because a label leaked backwards in time. This code goes out of its way to make that impossible, and then reports that it did not beat the benchmark.

The three ways to start it

1. Installed command. uv run covariance-denoiser run-offline-demo — declared in pyproject.toml under [project.scripts], pointing at covariance_denoiser.cli:main.
2. Shell wrapper. ./scripts/run_offline_demo.sh — changes to the repository root, then runs the same command.
3. Notebook. notebooks/01_offline_research_pipeline.ipynb — calls the same package functions stage by stage, so you can see the intermediate frames.

There is a second command, refresh-raw-cache, which is the only thing in the repository that touches a database. Nothing in a normal run, a test, or the notebook calls it.

Why the layout looks over-built for one experiment

Each stage is a separate module with one job, so a reviewer can check the target construction without reading the model code, and the tests can attack one contract at a time. The cost is that following a single number end to end means opening seven files. The payoff is that the tests in tests/unit/targets/ and tests/unit/models/ can pin the timing rules without spinning up the whole pipeline.

There is no config.toml. Every setting is a command-line flag with a default set in cli.py. This is the full list.

Trap

One tunable number is not a flag. In features/covariance_features.py, DEFAULT_TRAILING_VOL_DAYS = 21 sets the length of the trailing volatility feature and cannot be changed from the command line. If you run with --horizon-days 63, the target stretches to sixty-three days but that feature stays at twenty-one, and the naive rule shifts to sixty-three, so the feature and the benchmark stop lining up. Nothing warns you.

04Reading the data — raw_cache.py, prices.py

validate_raw_cache — refuse to run on the wrong file

In plain words

Before any arithmetic happens, it checks that the price file on disk is exactly the file the project expects, and stops with a clear message if not.

What it does

Input: a directory path. Output: a small frozen record holding a yes/no flag, a message, and the two file paths. Role: load_raw_prices calls it and raises FileNotFoundError if the flag is false, so no downstream module ever sees an unchecked file.

It runs nine checks in order: both files exist, the JSON parses to an object, all eight required metadata keys are present, the parquet columns are exactly ['date', 'asset', 'close'], the row count matches, the set of fund symbols matches, the first and last dates match, the frequency is "1d", the price field is "close", and is_adjusted_close is True.

Why check is_adjusted_close at all

Adjusted closing prices already fold dividends and share splits back into the price. Unadjusted prices contain a large fake drop on every split and every dividend date. Since the whole project is about the size of squared returns, one unadjusted split would create a false volatility spike big enough to move the results. The metadata flag makes that assumption a hard requirement rather than a hope.

build_log_return_matrix — long table to wide returns

wide_prices = prices.pivot(index="date", columns="asset", values="close").sort_index()

log_prices = np.log(wide_prices)
log_returns = log_prices.diff().dropna(how="any")
log_returns.index = pd.to_datetime(log_returns.index)
return log_returns
The formula

$$r_{i,t}=\log\left(\frac{P_{i,t}}{P_{i,t-1}}\right)=\log P_{i,t}-\log P_{i,t-1}$$

$P_{i,t}$ is the adjusted closing price of fund $i$ on day $t$. $r_{i,t}$ is its log return, a plain decimal, so 0.0090 means about +0.90 per cent. Log returns are used because they add up across days, which is what makes the target in section 05 a simple sum.

Trap

dropna(how="any") drops a whole date if any single fund is missing that day. It does not fill or interpolate. With this tracked file nothing is dropped, but on a fund that listed later, or on a half-day where one fund has no print, you would silently lose the other seven funds' returns for that date, and the following day's return would quietly span two calendar days. Nothing logs it.

05The thing being forecast — realized_variance.py

compute_equal_weight_portfolio_log_returns — eight funds into one basket

asset_simple_returns = np.expm1(returns)
portfolio_simple_returns = asset_simple_returns.mean(axis=1)
return np.log1p(portfolio_simple_returns).rename("equal_weight_portfolio_log_return")
In plain words

It turns eight funds' daily moves into one number: what a basket holding an equal dollar amount of each fund, rebalanced every day, actually returned.

The formula

$$r_{p,t}=\log\left(1+\frac{1}{N}\sum_{i=1}^{N}\left(e^{r_{i,t}}-1\right)\right)$$

$r_{i,t}$ is fund $i$'s log return on day $t$; $e^{r_{i,t}}-1$ converts it to a simple percentage return; $N=8$ is the number of funds; $r_{p,t}$ is the portfolio's log return. Reading it inside out: undo the log to get plain percentage moves, average those, then take the log again.

Why the long way round instead of averaging the log returns

Averaging log returns describes a basket you never rebalance and whose weights drift. Averaging simple returns first describes a basket you rebalance to equal weights every single day, which is what "equal weight" is meant to mean. The gap looks tiny on one day, but the whole project measures the sum of squared portfolio returns, so a systematic bias in the portfolio return becomes a systematic bias in the target. The repository's own journal records this as an audit fix. A unit test, test_equal_weight_portfolio_return_averages_simple_returns_first, locks it in place.

compute_forward_realized_variance_target — the label

equal_weight_returns = compute_equal_weight_portfolio_log_returns(returns=returns)
squared_equal_weight_returns = equal_weight_returns.pow(2)

# Rolling sum over the next `horizon_days` squared returns; shift aligns label to today.
forward_realized_variance = (
    squared_equal_weight_returns.rolling(window=horizon_days).sum().shift(-horizon_days)
)
What it does

Input: the wide return matrix, a horizon $h$, and whether to annualize. Output: one number per date, holding how bumpy the next $h$ days turn out to be. Role: this is the value the models try to predict. The last $h$ rows are empty, because their future has not happened yet.

The formula

$$\mathrm{RV}_{t,h}=\sum_{j=1}^{h}r_{p,t+j}^{2} \qquad\text{and}\qquad \mathrm{RV}^{\text{ann}}_{t,h}=\mathrm{RV}_{t,h}\cdot\frac{A}{h}$$

$r_{p,t+j}$ is the portfolio log return $j$ days after day $t$; $h$ is the horizon in trading days, 21 by default; $A$ is trading days per year, 252 by default. Note the sum starts at $j=1$, not $j=0$: day $t$'s own return is excluded. The scale factor $A/h$ turns a 21-day sum into a per-year rate, so a value of 0.03 means an annualized volatility of $\sqrt{0.03}\approx 17.3$ per cent.

Trap: the sign of the shift

.rolling(21).sum() looks backwards: at row $p$ it holds the sum over rows $p-20$ through $p$. .shift(-21) then moves that value 21 rows earlier, so it lands on row $p-21$ and covers rows $p-20$ through $p$, which are the 21 days strictly after $p-21$. Get the sign of the shift wrong, or shift by 20 instead of 21, and day $t$'s own return leaks into its own label. The test test_forward_realized_variance_uses_future_returns_only checks this on four hand-computed rows.

06Three covariance estimators

All three take the same window of returns — by default the last 63 days × 8 funds — and return an 8×8 covariance matrix with the fund names attached. Only the recipe differs.

estimate_sample_covariance — the plain estimate

def estimate_sample_covariance(returns_window: pd.DataFrame) -> pd.DataFrame:
    """Estimate sample covariance from aligned return observations."""
    return returns_window.cov()
The formula

$$\hat{\Sigma}_{ij}=\frac{1}{T-1}\sum_{s=1}^{T}\left(r_{i,s}-\bar{r}_i\right)\left(r_{j,s}-\bar{r}_j\right)$$

$T$ is the number of days in the window (63); $r_{i,s}$ is fund $i$'s return on day $s$ of the window; $\bar{r}_i$ is that fund's average return over the window. Dividing by $T-1$ rather than $T$ is the standard correction for having estimated the average from the same data.

covariance_to_correlation — strip the volatility out

The formula

$$C_{ij}=\frac{\Sigma_{ij}}{\sqrt{\Sigma_{ii}\,\Sigma_{jj}}}$$

$\Sigma_{ii}$ is fund $i$'s variance, so $\sqrt{\Sigma_{ii}}$ is its volatility. Dividing by both volatilities leaves a pure co-movement number between $-1$ and $+1$. The code clamps each variance at $10^{-12}$ before the square root so a dead, never-moving fund cannot cause a division by zero, then forces the matrix to be exactly symmetric and puts exact ones on the diagonal to undo floating-point drift.

estimate_ledoit_wolf_covariance — pull the estimate toward a simple shape

In plain words

It blends the noisy sample matrix with a very simple, very stable matrix, and works out the blend proportion automatically.

The formula

$$\Sigma_{\text{LW}}=(1-\delta)\,\hat{\Sigma}+\delta\,F,\qquad F=\mu I,\qquad \mu=\frac{\operatorname{tr}(\hat{\Sigma})}{N}$$

$\hat{\Sigma}$ is the sample covariance; $F$ is the target shape, here a matrix with the average variance $\mu$ down the diagonal and zeros everywhere else; $I$ is the identity matrix; $\operatorname{tr}$ sums the diagonal; $N=8$ is the number of funds; $\delta$ between 0 and 1 is the shrinkage intensity, chosen by the Ledoit-Wolf rule to minimise expected squared error. The code does not implement this; it calls sklearn.covariance.LedoitWolf and only re-attaches the fund names.

estimate_rmt_covariance — delete the noise directions

eigenvalues, eigenvectors = np.linalg.eigh(sample_correlation.to_numpy())

# Marcenko-Pastur upper edge for the noise bulk (T observations, N assets).
observation_count = float(len(returns_window))
asset_count = float(returns_window.shape[1])
aspect_ratio = observation_count / asset_count
lambda_plus = (1.0 + aspect_ratio**-0.5) ** 2

# Replace noise eigenvalues with their average rather than zeroing them out.
noise_mask = eigenvalues <= lambda_plus
if noise_mask.any():
    eigenvalues[noise_mask] = float(eigenvalues[noise_mask].mean())
In plain words

Break the correlation matrix into independent directions. Mathematics tells you how large a direction can look purely by luck when you only have sixty-three days of data. Any direction below that size is treated as noise and flattened to the average of all the noise directions. Rebuild the matrix from what is left.

The formula

Step 1, the noise ceiling from Marchenko-Pastur theory:

$$q=\frac{T}{N},\qquad \lambda_{+}=\left(1+q^{-1/2}\right)^{2}$$

Step 2, flatten every eigenvalue at or below that ceiling to their common average:

$$\tilde{\lambda}_k=\frac{1}{|\mathcal{N}|}\sum_{m\in\mathcal{N}}\lambda_m \quad\text{for every }k\in\mathcal{N},\qquad \mathcal{N}=\{\,m:\lambda_m\le\lambda_{+}\,\}$$

Step 3, rebuild, rescale the diagonal back to one, then reattach the volatilities:

$$\tilde{C}=V\,\operatorname{diag}(\tilde{\lambda})\,V^{\top},\qquad \Sigma_{\text{RMT}}=D\,\tilde{C}_{\text{norm}}\,D,\qquad D=\operatorname{diag}(s_1,\dots,s_N)$$

$T$ is days in the window (63); $N$ is funds (8); $q$ is the ratio of the two; $\lambda_+$ is the largest size a direction can reach from pure chance; $\lambda_m$ is the $m$-th eigenvalue of the sample correlation matrix, sorted ascending; $\mathcal{N}$ is the set of eigenvalues judged to be noise and $|\mathcal{N}|$ is how many there are; $V$ holds the eigenvectors as columns; $\tilde{C}_{\text{norm}}$ is the rebuilt matrix rescaled so its diagonal is exactly one; $s_i$ is fund $i$'s sample standard deviation over the window. Flattening to the average rather than to zero keeps the total of all eigenvalues unchanged, which keeps the funds' variances honest.

Across all 4216 windows in the tracked data, only one eigenvalue survives the cutoff in 4060 of them (96.3 per cent), and two survive in the remaining 156. The random matrix theory filter is, in practice, collapsing eight funds to a single common factor almost every day.

The weakness, stated honestly

Marchenko-Pastur theory describes what happens when both the number of funds and the number of days grow large together. Here $N=8$. Eight is not large. The cutoff $\lambda_+ = 1.8397$ is also completely fixed, because $q=63/8$ never changes, so the filter applies the same ruler to a calm market and a crisis. The repository's own GUIDE_OVERVIEW.md calls this "a filtering heuristic", which is the right description.

Trap: the condition number is mostly measuring volatility spread

The condition number of the cleaned correlation matrix in the last window is 7.57. The condition number of the cleaned covariance matrix is 91.08, twelve times larger. The extra factor is not noise; it is the spread of fund volatilities. Daily volatilities in that window run from 0.00261 (HYG) to 0.01325 (IWM), a ratio of 5.08, and covariance scales with volatility squared, so $5.08^2 = 25.8$. Three of the seven features are covariance condition numbers. They are partly reporting how different the funds' volatilities are, which is not what "denoising quality" is supposed to mean.

07The seven predictors — covariance_features.py

for end_index in range(lookback_days - 1, len(returns)):
    window_start = end_index - lookback_days + 1
    in_sample_window = returns.iloc[window_start : end_index + 1]

    # Three estimators share the same in-sample window; only post-processing differs.
    covariances = {
        "sample": estimate_sample_covariance(in_sample_window),

In plain words

Slide a 63-day window one day at a time across seventeen years. At every stop, build all three covariance matrices and squeeze them down to seven single numbers. Stamp the row with the last day of the window.

What it does

Input: the 4278×8 return matrix and a lookback length. Output: a 4216×7 table indexed by window-end date. Role: the left-hand side of the model. Runtime: about 8 seconds for the full history, because it fits 4216 × 3 = 12,648 covariance matrices in a plain Python loop.

The formulas behind the seven columns

Condition number of a covariance matrix, used three times:

$$\kappa(\Sigma)=\frac{\lambda_{\max}(\Sigma)}{\lambda_{\min}(\Sigma)}$$

Average pairwise correlation, over the pairs above the diagonal only:

$$\bar{\rho}=\frac{2}{N(N-1)}\sum_{i\lt j}C_{ij}$$

Trailing annualized volatility of the basket:

$$\sigma_t=\sqrt{A}\cdot\operatorname{sd}\!\left(r_{p,t-20},\dots,r_{p,t}\right)$$

$\lambda_{\max}$ and $\lambda_{\min}$ are the largest and smallest eigenvalues, so $\kappa$ is large when the matrix is close to being un-invertible; $C_{ij}$ is the correlation between funds $i$ and $j$; $N=8$, so there are $N(N-1)/2 = 28$ pairs; $\operatorname{sd}$ is the sample standard deviation with the $T-1$ divisor over the last 21 portfolio returns; $A=252$.

Why the row is stamped with the last day of the window, not the day after

A feature row stamped $t$ is built from returns up to and including day $t$, so it is knowable at the close of day $t$. The target stamped $t$ covers days $t+1$ to $t+h$. Joining them on the date therefore lines up "everything I know at the close of $t$" against "what happens next". Shifting the feature stamp forward by one day would throw away information; shifting it backward would leak.

Trap: the ratios divide by a number that is never small

The code guards the two ratio features with max(sample_condition_number, 1e-12). That guard can never fire: a condition number is a ratio of the largest to the smallest eigenvalue of a positive matrix, so it is always at least 1. The guard is harmless but it also gives false comfort. The real risk with these ratios is the opposite one — the denominator blowing up to 1396 in a stressed window, which squashes the ratio toward zero and is exactly the regime you care about.

08Timing and training — walk_forward.py, baselines.py

This is the part of the repository that matters. Everything else is bookkeeping.

The timing problem in one picture

A label stamped on day $t$ is a sum over days $t+1$ to $t+h$. You do not know it until the close of day $t+h$. So when you stand at day $t_0$ and forecast, the most recent label you are allowed to have trained on is the one stamped $t_0 - h$. The $h-1$ labels stamped after that are still being formed.

row:      ... 249  250  251 | 252 253 ... 271 | 272  273 ...
                             |                 |
                    train    |     PURGED      |  test
                  (0 .. 251) |   (252 .. 271)  | (272 .. 292)
                             |    20 rows      |
                             |                 |
label at row 251 covers returns 252..272, so it is known at row 272

generate_walk_forward_slices — where the gap comes from

# A target at position t uses returns t+1 through t+h and is known at t+h.
# Starting at min_train_size + h - 1 preserves the requested count of fully
# observed training labels while purging the h - 1 unavailable labels.
test_start = config.min_train_size + config.target_horizon_days - 1
while test_start + config.test_size <= sample_count:
    train_stop = test_start - config.target_horizon_days + 1
    train_slice = slice(0, train_stop)
    test_slice = slice(test_start, test_start + config.test_size)
    slices.append((train_slice, test_slice))
    test_start += config.step_size
The formula

For a fold whose test block begins at row $s$:

$$s_0=m+h-1,\qquad s_{k+1}=s_k+\Delta,\qquad \text{train}=[0,\;s-h+1),\qquad \text{test}=[s,\;s+n)$$

$m$ is min_train_size (252); $h$ is target_horizon_days (21); $\Delta$ is step_size (21); $n$ is test_size (21); $k$ counts folds from zero. The gap between the end of training and the start of testing is $s - (s-h+1) = h-1 = 20$ rows. The first test row is placed at $m+h-1$ rather than at $m$ precisely so that the training block still holds the full $m$ rows that were asked for.

Sample data
in — 4195 aligned rows, m=252 h=21 n=21 step=21 
generate_walk_forward_slices(sample_count=4195, config=...)
out — 186 folds 
fold   0: train rows [0, 252)   test rows [272, 293)   purged 252..271  (20 rows)
fold   1: train rows [0, 273)   test rows [293, 314)   purged 273..292  (20 rows)
fold 185: train rows [0, 4137)  test rows [4157, 4178) purged 4137..4156 (20 rows)

186 folds × 21 test rows = 3906 forecasts. The last 17 rows (4178 to 4194) are never tested, because they cannot fill a whole 21-row block.

Why chronological order alone is not enough

The usual rule is "train on the past, test on the future", which here would mean training on rows 0 to 271 and testing from row 272. That is wrong. The label stamped on row 271 is a sum over rows 272 to 292, which are the very days being forecast. Training on it hands the model the answer. Ordinary TimeSeriesSplit from scikit-learn makes exactly this mistake with overlapping forward-looking labels. The purge of $h-1$ rows is the fix, and test_walk_forward_slices_respect_train_before_test asserts the arithmetic directly.

lagged_observable_target = target.shift(target_horizon_days)
prediction = lagged_observable_target.loc[test_index]
if prediction.isna().any():
    raise ValueError("Naive forecast requires an observable lagged target for every test row.")
The formula

$$\hat{y}_t=\mathrm{RV}^{\text{ann}}_{t-h,\,h}$$

$\hat{y}_t$ is the forecast made at the close of day $t$; $\mathrm{RV}^{\text{ann}}_{t-h,h}$ is the annualized realized variance over days $t-h+1$ to $t$, that is, the month that has just finished. It became fully known at the close of day $t$ and not one minute earlier. In plain words: next month will be as bumpy as the month that just ended.

Trap the raise prevents

If the shift ran off the front of the series, .loc[test_index] would hand back empty values and the error metrics would quietly be computed over fewer rows, or over NaN. The explicit raise turns a silent distortion into a loud stop. It is one of very few places in the codebase that refuses to continue rather than coping.

run_walk_forward_models — fit, forecast, floor

# Ridge is not scale invariant. Fit the scaler on each training fold so
# condition numbers and decimal volatility receive comparable penalties.
ridge_model = make_pipeline(StandardScaler(), Ridge(alpha=ridge_alpha))
ridge_model.fit(train_features, train_target)
# A linear model is unconstrained, but variance cannot be negative. The
# zero floor is fixed before evaluation and applies to every fold.
ridge_raw_prediction = pd.Series(
    ridge_model.predict(test_features),
    index=test_features.index,
    name="ridge_raw_prediction",
)
ridge_prediction = pd.Series(
    ridge_raw_prediction.clip(lower=MIN_VARIANCE_FORECAST),
    index=test_features.index,
    name="ridge_prediction",
)
The formula

Standardize each predictor using the training fold's own average and spread:

$$z_{j}=\frac{x_{j}-\mu_{j}^{\text{train}}}{\sigma_{j}^{\text{train}}}$$

Then fit ridge regression, which is least squares with a penalty on the size of the coefficients:

$$\hat{\beta}=\arg\min_{\beta}\;\left\lVert y-Z\beta\right\rVert_{2}^{2}+\alpha\left\lVert\beta\right\rVert_{2}^{2} \;\;\Longrightarrow\;\; \hat{\beta}=\left(Z^{\top}Z+\alpha I\right)^{-1}Z^{\top}y$$

Finally clip the forecast into the range a variance can live in:

$$\hat{y}=\max\!\left(0,\;z^{\top}\hat{\beta}+\hat{\beta}_0\right)$$

$x_j$ is the raw value of feature $j$; $\mu_j^{\text{train}}$ and $\sigma_j^{\text{train}}$ are that feature's average and standard deviation computed only from the training rows of that fold; $z_j$ is the standardized value; $Z$ is the matrix of standardized training features; $y$ is the vector of training labels; $\alpha$ is --ridge-alpha, fixed at 1.0; $\beta$ is the coefficient vector and $\hat\beta_0$ the intercept; $I$ is the identity matrix. Setting the derivative of the objective to zero and solving for $\beta$ gives the closed form shown, which is what scikit-learn computes.

Why the scaler is inside the fold and not outside

Two reasons, and the second is the one people miss.

Scale. The seven features live on wildly different scales: condition numbers reach 1396 while trailing volatility sits near 0.12. Ridge penalizes all coefficients equally, so without standardization the condition-number coefficients would be crushed to nothing purely because their inputs are large. The penalty would be meaningless.

Leakage. If you standardized once over the whole history, the average and spread used on 2009 data would already contain 2020's numbers. That is a mild but real leak of the future into the past. Fitting the scaler inside make_pipeline means .fit() only ever sees the training rows of that fold.

The weakness, stated honestly

The zero floor fires on 784 of 3906 forecasts, 20.1 per cent. The most negative raw forecast is $-0.1555$, while the average realized value is $0.0158$. A model that predicts an impossible number one time in five is not being lightly corrected at the edges; it is badly miscalibrated and the clip is hiding how badly. The clip is applied before scoring, so the reported ridge error is better than the unclipped model deserves, and it still loses.

09Scoring and output files

The formula

$$\mathrm{MAE}=\frac{1}{n}\sum_{t=1}^{n}\left|y_t-\hat{y}_t\right| \qquad \mathrm{RMSE}=\sqrt{\frac{1}{n}\sum_{t=1}^{n}\left(y_t-\hat{y}_t\right)^{2}}$$

$y_t$ is the realized annualized variance, $\hat{y}_t$ the forecast, $n=3906$ the number of scored days. Mean absolute error treats every miss in proportion to its size. Root mean squared error squares first, so a few large misses dominate it. Both are in the same units as the target, so they can be compared directly against the average target value of 0.0158.

Why the two measures disagree in size but not in ranking

On mean absolute error the naive rule wins by a wide margin, 0.0106 against 0.0184. On root mean squared error the gap almost closes, 0.0340 against 0.0354. Both are far larger than the mean absolute error because realized variance has rare enormous spikes, and squaring lets those spikes swamp everything else. Neither model predicts the spikes, so on that measure both look similarly poor. The honest reading is that the ridge model is clearly worse on typical days and about equally helpless on the days that matter.

10The optional database refresh — clickhouse_refresh.py

In plain words

One command that goes to a ClickHouse database, pulls prices, and rewrites the parquet file and its metadata. Nothing else in the project calls it.

What it does

Input: connection settings, a date range, and a list of fund symbols. Output: overwrites raw_prices.parquet and raw_prices.metadata.json. Role: a one-time escape hatch. The metadata it writes is exactly the contract that validate_raw_cache checks, so the two ends match by construction.

Two things to know before running it

It overwrites without asking. There is no backup, no confirmation, and no dry-run. If the query returns fewer rows than expected, the tracked reference dataset is gone and the whole repository's results change.

The password is a command-line flag. That puts the database password into your shell history and into the process list, where any other user on the machine can read it. There is a .env file in the repository, but no code reads it, so it does not help.

.rolling(h).sum().shift(-h)Sum the next $h$ values and stamp the result on todayThe rolling window looks backwards and the shift is negative. Two sign flips that cancel. Change either one and today's own return leaks into today's label.
np.expm1 / np.log1pConvert log returns to simple returns and backThey are not decoration for exp(x)-1 and log(1+x). They keep precision for small $x$, which is exactly the size of a daily return. Also, the round trip only makes sense if you average in between; averaging log returns directly gives a different, wrong portfolio.

15If someone points at a line

The questionThe answer
"Where exactly is look-ahead bias prevented?"Three places, and they have to agree. (1) The target's .shift(-h) starts the sum at $t+1$, so a label never contains its own day. (2) generate_walk_forward_slices cuts training off $h-1$ rows before the test block, so no training label's window overlaps the test period. (3) StandardScaler lives inside the fold pipeline, so the standardization statistics come only from training rows.
"Prove the purge width is right, do not just assert it."Fold 0's last training row is 2009-04-01 and its first test row is 2009-05-01. The naive forecast for 2009-05-01 is 0.086617, and the label stamped 2009-04-01 is also 0.086617. The last label you are allowed to train on and the last label you are allowed to know are the same row. One row wider and you would be using the future.
"Why not just use scikit-learn's TimeSeriesSplit?"It splits in order but places the test block immediately after training. With labels that look 21 days forward, the last 20 training labels are partly made of test-period returns. This code purges those 20 rows; TimeSeriesSplit does not.
"Are the reported errors statistically valid?"No, and the README says so. Neighbouring 21-day targets share 20 of their 21 days, so the 3906 forecasts are nowhere near 3906 independent observations. MAE and RMSE here are descriptive comparisons, not a significance test. A proper test would need an overlap-aware standard error such as Newey-West.
"Why is ridge_raw_prediction in the output when you also report the clipped one?"So the clip is auditable. It fires on 784 of 3906 forecasts (20.1 per cent), with a worst raw value of $-0.1555$ against an average realized value of $0.0158$. Without that column nobody could tell how much work the floor is doing.
"What happens if I set --horizon-days 63?"The target window, the purge width, and the naive rule's lag all move to 63 automatically. DEFAULT_TRAILING_VOL_DAYS does not; it stays at 21. Nothing errors, and the trailing volatility feature quietly stops matching the horizon.
"How long does a run take?"About 20 seconds end to end on the tracked data. Roughly 8 of those are the feature loop, which fits 12,648 covariance matrices one at a time in Python. The 186 ridge fits are negligible by comparison.
"Why does the random matrix theory filter help conditioning less than shrinkage?"Two reasons. It filters the correlation matrix and then multiplies the volatilities back in, and the spread of fund volatilities alone contributes a factor of about 26 to the condition number in the last window. Ledoit-Wolf shrinks the whole covariance matrix, volatilities included. Comparing 91.08 to 9.12 is therefore not comparing like with like.
"Is eight funds enough for random matrix theory?"No. The theory is asymptotic in both $N$ and $T$, and $N=8$. On the real data the filter keeps exactly one eigenvalue in 96.3 per cent of windows, so it is effectively a one-factor model, not a nuanced clean-up.
"Where does the run write its files if I do not pass --output-dir?"Into outputs/demo under the repository root, resolved from the package's own file location. Before the fix in section 11 it was resolved from your current shell directory instead.

17Limitations, stated honestly

The sample is one universe, one horizon, one everything

Eight funds, one 63-day lookback, one 21-day horizon, one feature set, one fixed ridge penalty, one price history. Nothing was varied, so there is no way to tell whether the negative result is about denoised covariance features in general or about this particular corner. The upside is that nothing was tuned either, so the result is not the product of a search over settings.

The error measures cannot support a significance claim

Neighbouring targets share 20 of their 21 days. The 3906 forecasts contain far less independent information than the count suggests. Comparing 0.010610 to 0.018354 tells you the naive rule is better here; it does not tell you the gap is statistically significant, and the code makes no attempt to say that it is.

Condition numbers are a weak proxy for what practitioners care about

The project measures denoising quality by how well conditioned the matrix is. That is a numerical property, not a financial one. It does not test whether the cleaned matrix produces better portfolio weights, lower turnover, or better hedges — which is what covariance cleaning is actually used for. GUIDE_OVERVIEW.md is explicit that this separation is intentional, but it does limit what the negative result means.

The model is barely a model

A linear regression on seven features, with a penalty of 1.0 that was never tuned, predicting a quantity that is bounded below at zero and violently right-skewed. It fails the non-negativity constraint one time in five. A sensible alternative would be to model the logarithm of variance, which is roughly symmetric and cannot produce an impossible forecast. The negative result is therefore partly a statement about a poorly matched model, not only about the features.

No transaction costs, no investability, no out-of-sample data

There is no trading, so there are no costs, but there is also no evidence that a better variance forecast would have been worth anything. And the tracked file ends 2024-12-31, so every result on this page has been seen by whoever tuned the pipeline. There is no held-back period.
